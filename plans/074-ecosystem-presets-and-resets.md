# Feature Plan: Ecosystem starter presets and reset stylesheets

**Status:** Approved — implementing; see §7 for the resolved decisions and §9
for what has landed
**Created:** 2026-09-17
**Owner:** Pandwind maintainers

## 1. Summary and context

Two gaps show up as soon as someone tries Pandwind on an existing project:

1. **No starter preset per ecosystem.** The built-in `defaultPreset` carried a
   Chakra v1 palette (colors lowered and provenance annotated in `nlvnmzly`)
   until the palette-drop revision removed it: the remaining Chakra v1 flavor
   is the shared scale groups, and every palette now belongs to a preset
   subpath. `csstypePreset` is deliberately structural-only. A Tailwind
   project, a Panda project, or a shadcn/ui project still has to hand-write a
   preset before it can use `css()` with its own vocabulary.
2. **No baseline stylesheet.** Every ecosystem ships a reset/preflight
   (Tailwind's `@tailwindcss/preflight`, Panda's `preflight`, StyleX's docs
   guidance). Pandwind ships none, so adopting projects keep two resets or
   write their own.

Both are additive: the frozen API (`tw`/`css`/`cx`/`createDesignCss`,
`ClassNameStrategy`, codegen entry points) stays as-is, and everything here
lands on **new opt-in subpaths**. This plan is the design note `AGENTS.md`
requires before adding surface, and it is the follow-up that
`plans/072-preset-layers.md` §3/§8 explicitly deferred "until the styling
ecosystem benchmark exists and can measure their type-graph cost". That
benchmark now exists (`runtime-size.test.ts`, `tsc-performance` /
`test:tsc`), so the deferral condition is met.

The palette drop and the Tailwind v4 preset have shipped (§9); the measured
size lanes in `docs/src/content/docs/reference/size.md` (`xoonysyt`,
refreshed by the palette drop) give the baseline the remaining presets are
measured against.

## 2. Goals

- Ship `createShadcnPreset(options)` on `pandwind/preset/shadcn` with parity
  for the option set that <https://ui.shadcn.com/create> exposes: style, base
  color, theme (accent), chart color, heading/body font, radius, and the
  generated CSS-variable block.
- Ship a Tailwind v4 preset on `pandwind/preset/tailwindcss` derived from the
  installed `tailwindcss/theme.css` (colors, spacing multiplier, radii,
  shadows, breakpoints, font families), not from a hand-copied list.
- Ship a Panda preset on `pandwind/preset/panda` derived from
  `@pandacss/preset-panda`.
- Ship baseline stylesheets on `pandwind/reset/<ecosystem>`: at minimum
  `tailwindcss`, `panda`, `stylex`, plus Pandwind's own minimal reset.
- Keep every addition off the default path: importing `pandwind/css` with
  `defaultPreset` must not gain a single byte, and the new subpaths must
  appear as their own measured lanes.

## 3. Non-goals

- Do not change `csstypePreset`, `createCss`, `tw`, `cx`, or any existing
  export. `defaultPreset` keeps its property contract and stock scale groups;
  the only change to it is the removal of the Chakra v1 palette, which is what
  the palette-drop revision did.
- Do not replace Chakra v1 stock values in `defaultPreset` with Tailwind v4
  values. That is a separate product decision; this plan adds new presets
  beside it, and the shadcn/Tailwind presets are the migration path.
- Do not port a component library. The shadcn preset emits design tokens and
  the CSS-variable contract; component markup is out of scope.
- Do not implement icon-library selection (Lucide and friends are a runtime
  dependency, not a style concern) or the shadcn/create "Shuffle" UX.
- Do not add a second CSS compiler, a styled-system layer, recipes, patterns,
  or JSX factories.
- Do not vendor upstream CSS or token data without a provenance header,
  upstream permalink, and license notice.

## 4. Proposed design

### 4.1 Preset subpaths

Each ecosystem preset is a cohesive module under `src/preset/<ecosystem>.ts`
that owns its data, its `create*Preset` factory, and its provenance comments,
matching the existing locality rule for adapters:

```ts
import { createShadcnPreset } from "pandwind/preset/shadcn";
import { tailwindPreset } from "pandwind/preset/tailwindcss";
import { pandaPreset } from "pandwind/preset/panda";
```

- **Data files are generated, not hand-written.** Upstream scales come from
  the installed package (`tailwindcss/theme.css`, `@pandacss/preset-panda`,
  the shadcn base-color CSS variables) through a `scripts/promote-*.ts`
  generator, following the existing `promote-tailwind-fixture.ts` /
  `promote-panda-fixture.ts` prior art. The generated TypeScript is checked in
  with its provenance header and is regenerated by the script, so upstream
  drift is a visible diff instead of a silent divergence.
- **`createShadcnPreset(options)` is a factory, not a data dump.** `options`
  carry the create-page selections; the factory composes the base-color
  palette, the accent/theme override, the chart palette, the radius, and the
  font families into one preset. The same selections also produce the
  `:root` / `.dark` CSS-variable block, exposed as `preset.cssVariables` so
  the reset layer and the design-system bridge can consume it.
- **`tailwindPreset` follows Tailwind v4 semantics.** Tailwind v4 replaced the
  explicit `4: 1rem` space scale with `--spacing: 0.25rem` and
  `calc(var(--spacing) * n)`. Pandwind's Chakra-derived `space` scale already
  agrees for integers (`4` → `1rem`), so the preset can expose the same
  authored values; the difference only appears at values outside the explicit
  scale, and that is a documented limitation rather than a silent remap.
- **Gamut is an explicit decision, not a conversion accident.** The Tailwind
  v4 palette is authored in OKLCH and part of it is outside sRGB. The preset
  keeps the authored OKLCH string (CSS values are opaque to the runtime) and
  the plan records the conversion result for the sRGB-only consumers that
  need it, instead of silently clipping values into a different color.

### 4.2 Reset subpaths

```ts
import "pandwind/reset/tailwindcss";
import "pandwind/reset/panda";
import "pandwind/reset/stylex";
```

- Each reset is a static `.css` asset authored under `src/reset/` and copied
  into `dist/reset/` at build time. tsdown 0.23 supports a `copy` option, so
  `clean: true` still wipes first and the asset step is deterministic; the
  alternative (a string-exporting TS module) is the fallback if asset copying
  proves brittle for the package build.
- `package.json` maps each reset to its `.css` file directly. Consumers under
  Vite get `*.css` module typing from `vite/client`; consumers without it need
  their own declaration, which the docs must state.
- The reset content is a port, not a verbatim copy. Tailwind's preflight and
  Panda's preflight both reset the same box-model basics; the port keeps the
  upstream provenance header and license notice, and documents every
  intentional omission.
- Resets are independent of presets: a project may use `pandwind/reset/panda`
  with `tailwindPreset` if it wants. The docs must not imply a required
  pairing.

### 4.3 Naming, packaging, and evidence

New subpaths require the full surface ritual, in one revision:

- `packages/pandwind/package.json` exports (four conditions each:
  `pandwind`, `types`, `import`, `default`).
- `packages/pandwind/tsdown.config.ts` entries for the new `src/preset/*.ts`
  modules, plus `copy` for `src/reset/*.css`.
- `knip.json` production entries for the new public subpaths.
- `plans/evidence/package-surface.json` records, checked by
  `scripts/check-package-surface.ts`.
- `tests/package-exports.test.ts` and `tests/packed-consumer.test.ts` so the
  packed tarball actually resolves the new entries and ships the `.css`
  files.
- `apps/playground/src/lib/{editor-types.ts,editor-types.test.ts,sandbox-modules.ts}`
  if a preset is exposed in the playground editor.
- README and `docs/` reference pages for presets and resets.

### 4.4 Measured cost

- Importing a starter preset must be an obvious, measurable line item. Add one
  row per shipped preset to `tests/runtime-size.test.ts` / `runtime-budget.json`
  / `docs/src/content/docs/reference/size.md` / `benchmarks.md`, measured the
  same way as the current `createCss(csstypePreset)` and
  `createCss(defaultPreset)` lanes.
- `createShadcnPreset(options)` is a generic factory, so its type-graph cost is
  the real risk. Measure it with `test:tsc` before and after, and keep the
  factory's option type flat (no deep conditional composition) so consumer
  call sites stay cheap.
- Resets ship as CSS assets and therefore add nothing to the JavaScript
  runtime. Their cost is CSS bytes, reported separately from the JS lanes.

## 5. Risks and mitigations

- **Type-graph cost of a parameterized preset.** Mitigation: flat option
  object, `test:tsc` budget, and a documented fallback to per-preset constants
  (`shadcnNovaPreset`) if the factory type proves expensive.
- **Upstream drift.** Tailwind, Panda, and shadcn all change their defaults.
  Mitigation: generated data files plus a regenerate-and-diff check in CI.
- **License and attribution.** Each ported stylesheet and palette needs its
  upstream license notice. Mitigation: provenance headers and a license
  section in the docs, mirroring the Chakra v1 permalink comments added in
  `nlvnmzly`.
- **shadcn preset-code coupling.** The create page's `--preset b0` token is an
  undocumented, unpublished encoding. Mitigation: implement the options object
  first; treat code encode/decode as a separate, explicitly-owned codec with
  round-trip tests, or skip it and document the gap.
- **Surface creep.** Four presets and four resets is eight new subpaths.
  Mitigation: ship latest Tailwind, then latest Chakra, then
  `createShadcnPreset`, measuring each before the next, and add Panda and
  StyleX only if the cost is acceptable.
- **Semantic mismatch.** Tailwind v4 spacing is multiplicative and Panda's
  scales differ; a preset can look right in docs and diverge at unusual
  values. Mitigation: per-preset parity tests against the upstream package's
  own resolved tokens for every authored scale.

## 7. Resolved decisions

1. **Resets live inside `pandwind`** on `pandwind/reset/*`. The maintainer
   chose in-package subpaths over a separate `@pandwind/reset` package, so
   upstream CSS license and provenance notices ship with the presets that
   consume them.
2. **shadcn `--preset` codec:** the maintainer did not ask for the code
   interchange, so the factory ships an options object first. Encoding and
   decoding stay a separate, explicitly-owned codec with round-trip tests if
   they are ever wanted.
3. **Gamut:** ship Tailwind v4's OKLCH values as authored. No sRGB-converted
   variant, because CSS values are opaque to the runtime and a converted twin
   would be a second source of truth.
4. **Order:** latest Tailwind, then latest Chakra, then
   `createShadcnPreset`, then Panda. Panda measured at 44,424 B minified /
   12,788 B gzip and shipped (§7.29); StyleX is skipped with a recorded
   reason (§7.30).
5. **Reset scope:** one subpath per ecosystem reset, because the maintainer
   expects them to be used separately. Nothing is split further: a reset is
   whole, and overlapping box-model rules are merged rather than emitted as
   separate layered fragments. Pandwind also ships its own minimal reset.
6. **Retired palette:** the Chakra v1 palette the default preset used to carry
   is gone from `defaultPreset` and is not re-shipped. Its values survive only
   as the test fixture `packages/pandwind/tests/fixtures/fixture-preset.ts`, so
   behavior and typing tests keep a preset whose color values resolve through
   named tokens.
7. **Chakra sources of truth.** `pandwind/preset/chakra` is generated from the
   installed `@chakra-ui/react` by `scripts/promote-chakra-preset.ts`.
   `defaultConfig.theme` owns the scales and `defaultConfig.conditions`
   (104 keys) owns the conditions; `theme.conditions` does not exist at all.
   `getPreflightCss` is undefined — the global stylesheet is
   `defaultConfig.globalCss`, and it belongs to the future
   `pandwind/reset/chakra` lane instead of this preset. Probing must go
   through `system.css(style)`, which returns a flat declaration object:
   reading `out.css` returns `undefined` and produced a false conclusion
   during reconnaissance.
8. **Static groups versus conditional groups.** Every Chakra token entry is a
   `{ value }` record and hues nest one level deeper, so the generator flattens
   `group.key.key2.value` into dotted keys (`"$gray.50"`, `"$whiteAlpha.50"`,
   `"$bg.subtle"`, `"$fg.muted"`). Every `colors` key carries Pandwind's `$`
   sigil, because `resolveTokenValue` matches the authored value verbatim:
   without the sigil the generated key would be the only accepted spelling and
   the `$gray.700` this preset documents would leak through as a literal. With
   it, `tokenNameAliases` also registers the bare canonical form, so both
   `"$gray.700"` and `"gray.700"` resolve to the same token. Non-color groups
   stay bare (`"lg"`, `"md"`, `"10"`), matching the Tailwind lane, where only
   the color namespace is sigiled.
   Static groups ship through `define.tokens` and emit under `:root`. The
   mode-dependent groups (`semanticTokens.colors`, `semanticTokens.shadows`,
   `semanticTokens.radii`) ship through `defineSemanticTokens`, which merges
   into an existing group rather than replacing it, so one `colors` group holds
   the static palette and the semantic roles at once and a single `color`
   binding resolves both `gray.500` and `bg.subtle`.
9. **Light and dark selectors.** The token conditions are
   `_light: ":root &, .light &"` and
   `_dark: ".dark &, .dark .chakra-theme:not(.light) &"`, which is exactly what
   Chakra emits, and `base: ""` joins the preset condition map so
   `defineSemanticTokens` accepts it. `presetConditions` is spread first and
   every Chakra condition overlays it, so Chakra semantics win where the two
   disagree (`:first-of-type` over `:first-child`), while `_dark` and
   `_light` keep the Chakra selectors the semantic tokens depend on.
10. **Embedded references resolve at generation time.** All 112 `{...}`
    references in Chakra's theme point at static tokens, and Pandwind passes an
    embedded reference through unresolved. The generator therefore substitutes
    the literal: `{colors.gray.900}` becomes the hex read from the same theme,
    and `{colors.gray.900/10}` becomes
    `color-mix(in srgb, <hex> 10%, transparent)`, which is the declaration
    `system.css` emits with its own `--chakra-*` variable inlined. A
    whole-value reference (`radii.l1 = "{radii.xs}"`) stays a Pandwind token
    reference, because Pandwind does declare that variable. No generated value
    ever names a `--chakra-*` variable, since Pandwind never declares one.
11. **Value normalizations.** Chakra's `blurs` scale is dropped whole, not
    normalized: it reaches CSS only through Chakra's `blur` utility, which
    writes a `--blur` custom property rather than a property Pandwind binds,
    so its `:root` declarations would be bytes no authored style could read.
    Numeric `lineHeights` and `zIndex` are stringified,
    because Pandwind token groups are string records. Composite
    `borders.*` (`"1px solid"`) bind only to the `border` properties that
    accept a shorthand. `l1`/`l2`/`l3` stay whole-value references. Negative
    spacing stays literal, because Chakra ships no negative tokens and
    `presetConditions` has no negative-spacing override.
12. **Property bindings.** Chakra's own compile table drives the property map:
    `padding*`/`margin*`/`gap*`/`inset*`/`top`/`right`/`bottom`/`left`/
    `scrollMargin*`/`borderSpacing` read `spacing`;
    `width`/`height`/`min*`/`max*`/`flexBasis` read `sizes`;
    `borderRadius` and its eight corner variants read `radii`; `border` plus
    the four sides read `borders`; `boxShadow` and `textShadow` read
    `shadows`; the typography properties read their matching group; `color`
    and the twelve other color properties read `colors`; `zIndex`,
    `aspectRatio`, `animation`, `cursor`, `transitionDuration`, and
    `transitionTimingFunction` read their own group with named keys only
    (`zIndex: "10"` stays literal upstream and here). The preset rebinds
    `inset*` and the four offsets from Pandwind's `sizes` to `spacing`,
    because Chakra reads those properties from its spacing scale — a real
    semantic difference, not a spelling one. The scroll family follows the
    same probe rather than one blanket rule: `scrollMargin` and its four
    physical sides, `scrollPadding` and its four physical sides, and the
    `scrollPaddingInline` / `scrollPaddingBlock` shorthands all resolve to
    `var(--chakra-spacing-4)` upstream and therefore bind `spacing`. The
    logical `scrollMarginInline` / `scrollMarginBlock` /
    `scrollMarginInlineStart` / `scrollPaddingInlineStart` /
    `scrollPaddingBlockStart` forms emit the raw length `4` and stay
    unbound, because binding a property Chakra treats as a raw length would
    accept token names upstream rejects. `borderWidth*` and
    `borderBlockWidth` / `borderInlineWidth` keep Pandwind's own `borders`
    group (`none`, `1px`, `2px`, `4px`, `8px`), which is a width scale,
    while `chakraTokens.borders` holds `1px solid` composites that are only
    valid for the `border` shorthand; `outline`, `outlineWidth`, and
    `outlineOffset` keep their stock bindings too, because Chakra has no
    utility entry for those properties at all. `transition` and
    `transitionProperty` bind to the composed groups §7.19 describes.
13. **Condition map.** All 104 Chakra conditions ship as `_<name>`, including
    the array-valued `hover` (hover-capable media query plus the state
    selector) and the raw `dark`/`light` entries, which the token conditions
    replace with Chakra's own two-selector form. Chakra's breakpoints
    (`sm`–`2xl`) are not conditions upstream; they join the map as
    `@media (min-width: …)` using the pixel widths from
    `theme.breakpoints`, which keeps the stylesheet's ordering policy able to
    place narrower rules first regardless of scan order.
14. **Color palettes.** `defineColorPalettes` is sourced from the 16 static
    color roots plus the semantic `bg`, `fg`, and `border` roots. The four
    singleton roots (`transparent`, `current`, `black`, `white`) map to the
    empty suffix and therefore to the virtual `colorPalette` token. Chakra
    spells its last role `focus-ring` while Pandwind builds the suffix
    verbatim, so the preset maps it to `focusRing` and the divergence is
    asserted in the parity test.
15. **Keyframes are deferred, so `animations` is dropped.** Chakra ships 33
    keyframes and its `animations` tokens reference them by name, but a
    Pandwind preset has no keyframes hook, so a shipped shorthand names an
    animation no stylesheet declares and shipping 33 unconsumed keyframe
    strings would be dead data. The group is absent and the project owns both
    the shorthand and the `@keyframes` body. Superseded: the first shipped cut
    carried the group's four names; §7.32 records the drop.
16. **Slash-containing size keys.** Chakra's `sizes` group carries fraction
    keys (`1/2`, `1/3`, …) and Pandwind reads `/` as its color
    opacity modifier. The generator renames them to the `1-2`, `1-3` form and
    the parity test asserts the rename, so no token name can be parsed as a
    slash modifier.
17. **Documented divergences.** `blur` and `backdropBlur` are Chakra
    utilities backed by `--blur`/`--backdrop-blur`, not CSS properties, so
    `chakraProperties` does not bind them and `filter`/`backdropFilter` stay
    literal. `scrollbarWidth` stays `true` (Chakra reads it from `sizes`,
    but its documented values are the `thin`/`auto` keywords). `textEmphasisColor`
    stays bound to `colors`, which is a Pandwind-side addition over Chakra's
    literal handling. `backgroundColor`/`background` emit one declaration where
    Chakra also writes its `--bg-currentcolor` plumbing.
18. **Fixture lane unchanged.** `packages/pandwind/tests/fixtures/runtime-preset-css.ts`
    keeps importing `defaultPreset` with hex literals; it exercises the
    authored-literal path rather than a named palette, so the palette drop does
    not reach it. The named-palette lane is `runtime-preset-cx.ts`,
    `runtime-preset-fixture.ts`, and `runtime-preset-all.ts`, which all read
    the `fixturePreset` fixture from §7.6. The type-graph scenario in
    `packages/pandwind/tests/fixtures/tsc/css-default.ts` reads the same
    fixture, so it measures a named-palette workload again instead of the
    authored-literal one the palette drop left it with.
19. **Transitions are composed, not transcribed.** Chakra reaches its
    `transition` and `transitionProperty` scales only through utilities that
    take a keyword: `transition: "colors"` expands to a property list plus a
    duration and an easing, and `transitionProperty: "colors"` writes a bare
    property list. Pandwind binds one property to one token value, so the
    generator flattens every `transition` keyword into the single
    `property duration timing` shorthand a project writes by hand
    (`all 150ms cubic-bezier(0.4, 0, 0.2, 1)`) and ships the
    `transitionProperty` keyword lists verbatim as their own group. Each
    group is therefore exactly the vocabulary its own utility accepts — nine
    keywords plus `none` for the shorthand, five keywords for the property
    list — and neither group is padded with keywords the other utility owns.
    `transitionProperty: "all"` is not a Chakra value, so it stays authored
    CSS, which the group's inherited strictness already accepts. Both groups
    are composed in the generator instead of reading a stock Pandwind group,
    because Pandwind's own `transition` map (`none`/`slow`/`fast`) is not
    Chakra's vocabulary.

20. **Panda sources of truth.** `pandwind/preset/panda` is generated from the
    installed `@pandacss/config@1.12.1` by `scripts/promote-panda-preset.ts`.
    The resolver is handed an absolute config path that need not exist, so no
    project override can reach the checked-in module: `theme.tokens` owns the
    authored scales, `theme.breakpoints` the five pixel widths, the resolved
    `conditions` map the 107 selectors, and the `transition` and
    `transitionProperty` utilities the two keyword vocabularies. The generated
    header names the provenance and the deliberate divergences.
21. **Static groups versus the two composed groups.** Fourteen groups ship
    Pandwind's static token shape (`aspectRatios`, `borders`, `easings`,
    `durations`, `radii`, `fontWeights`, `lineHeights`, `fonts`,
    `letterSpacings`, `fontSizes`, `shadows`, `colors`, `spacing`, `sizes`)
    and hold 411 values. `transitions` and
    `transitionProperties` are composed by the generator (§7.26) and are the
    two groups Panda's `theme.tokens` does not publish. Every static value is
    asserted equal to what the installed resolver renders for the same path.
22. **Property bindings are derived, not transcribed.** `pandaProperties`
    carries 143 bindings: 115 follow from a utility's own `values` key naming a
    shipped group, and 28 are hand bindings because their utilities are aliases
    rather than scale readers — the thirteen sizing shorthands (`width`,
    `height`, `min*`, `max*`, `blockSize`, `inlineSize`, `flexBasis`), the
    thirteen spacing ones (`margin*`, `inset`, `borderSpacing`), and the two
    composed transition vocabularies. Group sizes: `spacing` 69, `colors` 23,
    `sizes` 14, `borders` 12, `radii` 9, `durations` 4, `easings` 2,
    `shadows` 2, and one each for `aspectRatios`, `fonts`,
    `fontSizes`, `fontWeights`, `letterSpacings`, `lineHeights`,
    `transitions`, `transitionProperties`. A utility that resolves against a
    scale but names no CSS property Pandwind declares — `borderBottomRadius`,
    `borderSpacingX`/`Y`, `boxShadowColor`, `divideColor`, `focusRingColor`,
    `focusRingOffset`, `gradientFrom`/`To`/`Via`, `textShadowColor`, and the
    five side radii — is not bound and is asserted as its own list, because a
    binding for it would be inert data.
23. **Properties Panda has no token scale for keep Pandwind's bindings.**
    `borderWidth`, `outlineWidth`, and `zIndex` ship Pandwind's own groups
    (`none`, `1px`, `2px`, `4px`, `8px` for the widths), `cursor` and
    `opacity` stay `true`, `outlineOffset` reads `spacing`, `scrollbarWidth`
    reads `sizes`, and `filter` / `backdropFilter` stay literal because Panda
    reaches its blur values only through `--blur` custom properties.
24. **Conditions and breakpoints.** All 107 Panda conditions ship as
    `_<name>`, including `_hover = "&:is(:hover, [data-hover])"`,
    `_icon = "& :where(svg)"`,
    `_placeholder = "&::placeholder, &[data-placeholder]"`, and
    `_dark = ".dark &"`. `pandaConditions` ends at 112 keys: the 107 upstream
    conditions, the 89 stock `presetConditions` — none dropped, and Panda's
    selector winning wherever the two maps disagree — and the five
    breakpoints, which Panda does not model as conditions and which join as
    `@media (min-width: …)` so the stylesheet's ordering policy can still
    place narrower rules before wider ones regardless of scan order.
25. **Colors ship Panda's own paths and no `colorPalette` map.** The 26
    color roots keep Panda's order (`current`, `black`, `white`,
    `transparent`, then the 22 hues) and 246 values. Every key is spelled
    `name`, the spelling Panda itself writes, so `color: "red.500"` is the
    token reference and resolves to `#ef4444`; `transparent` ships Panda's
    `rgb(0 0 0 / 0)`. No `colorPalette` map ships: Panda's palette mechanism
    is a recipe-time concern and Pandwind has no recipe lane. Superseded: the
    first shipped cut carried the `$` sigil with the bare path as its alias,
    which `resolveTokenValue`'s verbatim match made the only way to spell
    `"$red.500"` as a token; the maintainer dropped the sigil because a Panda
    project writes the bare path, so the preset now accepts exactly one
    spelling per token and `color: "$red.500"` passes through as a literal.
26. **Transitions are composed, not transcribed.** As with Chakra (§7.19),
    Panda reaches its `transition` and `transitionProperty` scales only
    through utilities that take a keyword. The generator flattens each
    `transition` keyword into the single `property duration timing` shorthand
    Pandwind binds, so `transitions.colors` is seven properties with
    `150ms cubic-bezier(0.4, 0, 0.2, 1)`, and it ships the
    `transitionProperty` keyword lists verbatim as their own group, so
    `transitionProperties.colors` is
    `"color, background-color, border-color, outline-color, text-decoration-color, fill, stroke"`.
    Neither group is padded with keywords the other utility owns, and
    `transitionProperty` does not exist in stock Pandwind at all, so this
    preset is its only source.
27. **Dropped scales.** `blurs` is dropped whole: Panda reaches it only
    through its `blur` / `backdropBlur` utilities, which write `--blur`
    custom properties instead of a CSS property Pandwind binds.
    `keyframes`, `textStyles`, `containerSizes`, the patterns, and the
    recipes are dropped for the same reason — Pandwind binds no property to
    them — and the `animations` group goes with them, so a project that writes
    `animation: "spin"` declares both the shorthand and its own `@keyframes`
    rule, the policy §7.15 set for Chakra and §7.32 unified across the presets.
28. **Dotted steps ship as authored.** Panda writes `spacing` and `sizes`
    with dotted steps (`"0.5"`, `"1.5"`, … through `"5.5"`), and the
    preset keeps them rather than renumbering them, so an authored
    `padding: "0.5"` resolves the value Panda would write for the same key.
29. **Measured lane.** `createCss(pandaPreset)`: 44,424 B minified /
    12,788 B gzip, budgeted at 45,350 / 13,050 — between `tailwindPreset`
    (40,314 / 13,169) and `chakraPreset` (51,166 / 13,810). The whole catalog
    ships because esbuild cannot drop unreferenced object entries; a
    hand-pruned subset would be a second source of truth.
30. **StyleX is skipped, with a recorded reason.** StyleX publishes no token
    preset to generate one from, and the community bridge
    (`@stylexjs/open-props`) is deprecated, so there is no upstream source of
    truth for a `pandwind/preset/stylex` and no reset of its own to port.
    `pandwind/reset/pandwind` is the documented stand-in for a project leaving
    StyleX (§4.2), and the docs already say so.
31. **Naming.** `reset` and `preset` differ by one letter, and the maintainer
    rejected "preflight" as the replacement, so both subpaths keep their
    current spelling and the distinction lives in
    `docs/src/content/docs/api/resets.md` ("Reset versus preset"). Revisit
    after this lane if the pair keeps reading as a typo.
32. **Animations groups dropped.** No starter preset ships an `animations`
    group. Tailwind's `--animate`, Chakra's `animations`, and Panda's
    `animations` scales are all shorthands whose `@keyframes` bodies live in
    the upstream project's own stylesheet rather than in the theme data a
    preset reads, so a bound `animation` token named an animation nothing
    declared. The maintainer's call was to drop the group rather than ship
    dead names, which also removes the `animation` property binding from all
    three presets (`animationDelay`, `animationDuration`, and
    `animationTimingFunction` keep their `durations` / `easings` bindings).
    A build-time `keyframes()` utility that emits project-authored
    `@keyframes` is the follow-up lane (§9).

## 8. Approval gate

`AGENTS.md` freezes the user-facing API and requires a written plan plus an
explicit maintainer go-ahead before new surface lands. This document is the
plan; implementation starts only after the go-ahead, and the answers to §7
decide the first revision's scope.
