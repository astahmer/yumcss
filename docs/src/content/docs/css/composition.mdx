Keep styles as objects until they reach the element. YumCSS can then choose the
last declaration for each property and condition before producing a class
string. No class-name parsing or `cx()` is needed.

## Authored objects: css(x, y, z)

`css()` accepts several preset-checked style objects. Later declarations win;
conditions merge independently:

```ts
const base = { padding: 4, color: "$slate-700" } as const;
const active = { color: "$blue-600", _hover: { color: "$blue-700" } } as const;

const styles = css(base, isActive && active, props.styles);
```

Here `props.styles` has type `AtomicStyleProps<typeof css>`. `false`, `null`,
and `undefined` arguments are skipped. Use `css.class(x, y, z)` when you want
the final class string immediately.

## Compiled maps: css.props(x, y, z)

A `css()` call returns a **compiled declaration map**: keys identify declarations
and values are their classes. Keep that map when another component will compose
it. Use `ReturnType<typeof css>` for a component's compiled-style prop:

```tsx
import { css } from "./css";

const base = css({ display: "flex", padding: 4 });

type BoxProps = {
	xcss?: ReturnType<typeof css>;
	children?: React.ReactNode;
};

export const Box = (props: BoxProps) => (
	<div {...css.props(base, props.xcss)}>{props.children}</div>
);

<Box xcss={css({ padding: 6, _hover: { backgroundColor: "$slate-100" } })} />;
```

`xcss` is a prop convention, not a special API. Any compiled map can cross this
boundary. Put the override last so it wins per declaration, including conditions.
The inputs should share a preset and class-name strategy.

**Pass compiled maps to `css.props()`, not back into `css()`.** `css()` compiles
CSS values; `css.props()` composes the already compiled classes and returns
`{ className, style }` for the host element.

## Variants without a recipe API

Variants are ordinary maps of `css()` results. Their keys provide the prop types,
and selecting a variant is a property lookup:

```tsx
import { css } from "./css";

const button = {
	base: css({
		display: "inline-flex",
		alignItems: "center",
		borderRadius: "md",
		fontWeight: "medium",
	}),
	size: {
		sm: css({ paddingInline: 2, height: 8 }),
		md: css({ paddingInline: 4, height: 10 }),
	},
	tone: {
		primary: css({
			backgroundColor: "$blue-600",
			color: "$white",
			_hover: { backgroundColor: "$blue-700" },
		}),
		ghost: css({
			backgroundColor: "transparent",
			color: "$slate-900",
			_hover: { backgroundColor: "$slate-100" },
		}),
	},
};

type ButtonProps = {
	size?: keyof typeof button.size;
	tone?: keyof typeof button.tone;
	xcss?: ReturnType<typeof css>;
	children?: React.ReactNode;
};

export const Button = (props: ButtonProps) => (
	<button
		{...css.props(
			button.base,
			button.size[props.size ?? "md"],
			button.tone[props.tone ?? "primary"],
			props.xcss,
		)}
	>
		{props.children}
	</button>
);

<Button xcss={css({ borderRadius: "full" })}>Rounded</Button>;
```

Compound variants are plain conditional inputs, such as
`props.tone === "ghost" && button.size.sm`. There is no recipe runtime or
class-string merger to ship for this pattern.

## When inputs might be dynamic

`css.props()` also carries inline custom properties from `css.vars()` and
parameterized groups. If a component accepts static maps **or** dynamic carriers,
derive its input type from the projection:

```tsx
type PanelProps = {
	xcss?: Parameters<typeof css.props>[number];
};

const panel = css({ display: "flex" });
const Panel = (props: PanelProps) => <section {...css.props(panel, props.xcss)} />;

<Panel xcss={css.vars({ opacity: runtimeOpacity })} />;
```

Spread the whole result: using only `className` would lose the inline `style`.
This broader input type also permits arrays and strings. Plain strings are
appended; `css.props()` does not resolve conflicts inside them. Prefer a compiled
map for overrides. See [dynamic styles](/css/dynamic-styles/).

## What the build removes

The extractor replaces provably static `css()` calls with declaration maps and
`css.class()` calls with strings. It can also fold resolvable composition and
`cx()` calls. Runtime prop values and selections can still need a small merge;
"static CSS" does not mean every surrounding JavaScript expression disappears.
See [extraction](/css/extraction/) for the supported analysis boundaries.

## Use cx() for class-string conflicts

Reach for `cx()` only when you must merge already flattened classes, such as an
existing `className` prop or Tailwind utilities. Once declarations become one
string, a merger must recover their property metadata:

```ts
import { createCx } from "yumcss/cx";
import { css } from "./css";

const cx = createCx({ css });
cx(css.class({ color: "$red-500" }), externalClassName);
```

It accepts strings, compiled maps, variable carriers, nested arrays, and falsy
inputs. Recognized YumCSS atoms merge last-wins. Unknown classes are kept and
deduplicated; their CSS conflicts cannot be inferred. Tailwind merging requires
the generated conflict data; see [cx() with Tailwind](/tailwind/tw/#merging-with-cx).

For your own component APIs, retain maps and use `css.props()` first.
